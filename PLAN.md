# Drishti — Phase Plan

Source spec: [Drishti — Engineering Spec for the Coding Agent](https://claude.ai/artifact/2HvZ4v6sNg9cxYW5AWAA8V) (rev 17). Section numbers (§), features (F1–F10) and decisions (D1–D16) below refer to it.

The app is built in 16 phases (P0–P15), ordered by dependency. Each phase ends with the same gate (below). A phase is done when its automated tests pass. Its on-device checks get queued for later.

## Changes from the spec (agreed with the user, 2026-11-06)

| Spec item | Change |
| --- | --- |
| §11 day schedule (M0–M3) | Not used. Phases are ordered by dependency, with no calendar. |
| D16 VLM choice | Not picked yet. The server ships two switchable VLM services, **OpenRouter** and **Vertex AI**, behind one `VlmClient`. The model is a config value. A benchmark script (P3) is for comparing models later. No direct Gemini API, OpenAI or Groq clients. |
| §5 detector "pick one" | Both **YOLO11n** and **EfficientDet-Lite0** are wired behind one `Detector` interface. Config picks one. The choice is made after the device benchmark (DT-6.1). |
| F5 offline STT (stretch) | Optional last build phase (P13), after everything else works. |
| Repo | Public git repo, initialised in P0. |
| F8/§7 Prisma settings for Hindi and Hinglish (found in P2) | Live tests showed realtime Prisma rejects language lists (`hi-IN,en-IN`), and `codemix` returns Devanagari even for English words. Hindi and Hinglish use `language_code=hi-IN` with `format=transliterate` (Latin output, e.g. "is ko rahul ke naam se save karo"). The command router matches romanised keywords only. |
| §7 number-to-words helper (found in P2) | Dropped. Timbre normalises digits itself when `language` is explicit ("42" → "बयालीस"), per the Gnani text normalisation guide. |
| §5 frame resizing and OCR (found in P0) | VisionCamera is now v5, and `vision-camera-resize-plugin` only supports v4. Frames are resized with `react-native-nitro-image` (`convertFrameToImage` → `resize`). No v5 OCR frame plugin exists, so F7 runs ML Kit (`@react-native-ml-kit/text-recognition`) on a captured photo. |
| D16 / P3 benchmark (user, 2026-11-07) | Vertex testing and model benchmarking are paused until the app is complete. Then, benchmark models on OpenRouter, preferring open-source ones. Interim model: OpenRouter `google/gemini-3.5-flash-lite`. |
| F6 prompt (found in P3) | Rules in English plus a per-language instruction (language, script, direction words), instead of the full prompt in each language. No "numbers as words" rule. |
| F3 threshold, alignment and crop (found in P8) | Threshold starts at 0.5, not 0.65: the shipped MobileFaceNet's LFW threshold is cosine 0.27, and laptop photos gave 0.82 same person vs ≤ 0.14 different people. An ambiguity margin (0.08 over the runner-up) makes lookalikes unknown. Faces are aligned to the InsightFace 112×112 template from ML Kit's eyes and mouth corners; the crop is 2.2× the face box, not 20% margin. |
| §5 camera frames (found in P8) | Frames are 1280×720 YUV instead of 640×480 RGB, so ML Kit can read them and faces reach 80 px at ~1.2 m. |

## Phase gate (end of every phase)

1. **Automated tests:** run the phase's Jest/pytest tests plus all earlier ones. All must pass, and no test may spend Gnani or VLM credits unless it is marked `live`.
2. **Live checks (laptop, opt-in):** run them only where the phase lists them, using real keys, and run each one once. Record the output in the phase's LIMITATIONS entry.
3. **Device checklist:** list the phase's `DT-x.y` checks in `LIMITATIONS.md` → *Pending device tests*. These don't block the next phase. When the user runs one, they record pass/fail there. A failure becomes a limitation entry and gets a fix in a later phase.
4. **Log limitations:** add a section for the phase to `LIMITATIONS.md` (format below). Cover what doesn't work, what is stubbed, measured vs target numbers, "verify" items still unverified, and any workarounds.
5. **Commit:** small, focused commits pushed as work progresses (one logical change each, prefixed `P<n>: `), not one big commit per phase. Plain message only, with no co-author, signature or "generated by" lines.

### LIMITATIONS.md format

```markdown
## P<n> — <title> (<date>)
- **Status:** automated tests pass (<count>) | live checks: <done/skipped>
- **Limitations:**
  - L<n>.1 <what doesn't work or is missing> — impact: <who/what it affects> — plan: <fix phase / accepted / post-contest>
- **Unverified assumptions:** <spec "verify" items not yet confirmed>
- **Measurements:** <stage: measured vs target>, or "none yet"

## Pending device tests
| ID | Check | Phase | Result | Date | Notes |
```

## P0 — Repo, tooling, first dev build

**Goal:** a monorepo that builds, plus an APK on the phone that shows a camera preview and loads a TFLite model.

- **Every native package from §5 is installed now**, so there is a single rebuild: vision-camera with its worklets runtime, resize plugin, fast-tflite with nitro-modules and the GPU-enabled config plugin, the ML Kit face detector plugin, the ML Kit text recognition plugin, a PCM recorder, expo-audio, expo-speech, expo-sqlite, expo-file-system, expo-haptics, expo-keep-awake and netinfo. Exception: `@react-native-voice/voice` waits for P14.

- Minimal screen: full-screen camera preview, plus a "model loaded: <name>, <ms>" label for both detector `.tflite` files (bundled assets).
- `server/`: Python 3.11, FastAPI app factory, `pydantic-settings` config, pytest set up, Dockerfile.
- Start the first EAS development build as early as possible (the free queue can take 90+ min).

Automated tests:

## P1 — Server skeleton: auth, rate limit, health

Work:
- `Authorization: Bearer <APP_TOKEN>` on every route, including the WebSocket handshake.
- Per-token rate limit (default 30 req/min, configurable), in memory.
- `GET /health` → `{"ok":true}`.
- Logging: timings and error codes only, never transcripts or images (§9).
- Settings: `GNANI_API_KEY`, `APP_TOKEN`, `VLM_PROVIDER` (`openrouter` | `vertex`), `VLM_MODEL`, `OPENROUTER_API_KEY`, `VERTEX_PROJECT` / `VERTEX_LOCATION`, `RATE_LIMIT_PER_MIN`.

Automated tests: missing or wrong token → 401 (HTTP and WS). The 31st request in a minute → 429. Health returns ok. A log-capture test asserts that request bodies are never logged.

Live checks: none.

Device checks: none.

## P2 — Gnani relay: /tts and /stt

**First:** verify every Gnani note in §7 against docs.gnani.ai and log differences. That covers auth header, endpoints, sample-rate header, `prisma-v3.0`, `codemix`, voice names per language, and whether v2.5 is needed for Hinglish.

Work:
- `GnaniTts` (Timbre REST): text ≤ 200 chars (longer text → 400), a language → voice map, MP3 output. On 429, one retry with backoff. Calls are serialised per request when the account allows only one at a time.
- Number-to-words helper per language (hi, hi-en, en, ta), used before every TTS call.
- `POST /tts` → `audio/mpeg`.
- `GnaniStt` WebSocket relay: the client sends a `{"lang":…}` JSON frame, then binary 16 kHz 16-bit mono PCM frames, then `{"type":"end"}`. The server forwards to Prisma at real-time pace. Hinglish uses codemix output. The server returns `{"type":"final",…}` or `{"type":"error","code":…}` and then closes.
- Map 402 (credits exhausted) and 429 to clear error codes.
- `scripts/stt_probe.py` and `scripts/tts_probe.py`: laptop scripts that stream a WAV file or speak a line through the local server.
- Record fixtures once: 5–10 short WAV clips (Hindi, Hinglish, English, Tamil, plus some commands) with their real transcripts saved alongside.

Automated tests (fakes, no credits): number-to-words tables, TTS length guard, retry-once on 429, STT frame protocol and close behaviour against a fake Prisma that replays fixtures, error-code mapping.

Live checks: one TTS line per language. One STT fixture per language. Note the latency of each and the credits consumed, so we can estimate the credit-to-minute rate (open question §11).

Device checks: none.

## P3 — VLM services, /ask pipeline, benchmark script

Work:
- `VlmClient` interface: `stream(system, image_jpeg, text, max_tokens, temperature) → async iterator of text deltas`.
- `OpenRouterVlm` (OpenAI-compatible streaming API, model from config).
- `VertexVlm` (Gemini on Vertex AI via `google-genai` in Vertex mode, streaming). Locally it authenticates with ADC, and on Cloud Run with the service account, so it needs no key file. Location is configurable. Verify which Gemini models are served in `asia-south1`.
- `VLM_PROVIDER` + `VLM_MODEL` select the provider and model at startup, with no code change.
- System prompt builder with the F6 rules, in the target language.
- Sentence splitter on `. ? ! ।`. It streams, so a sentence is emitted the moment its terminator arrives.
- `POST /ask` (multipart: question, lang, detections JSON, names JSON, image ≤ 512 px) → SSE. A Timbre call starts as soon as each sentence completes. `sentence` events are emitted strictly in order, and `done` carries `{vlm_first_token, first_sentence, first_audio, total}`.
- `scripts/bench_vlm.py`: runs a fixed set of 5–10 images × questions (in `server/bench/`) against a list of `provider:model` pairs given on the command line. It prints and saves a CSV of TTFT, first-sentence time and total time (median and p95) for each model.

Automated tests: the splitter (including `।`, decimals and abbreviations), the prompt builder, /ask ordering with a fake VLM and fake Timbre where sentence 2's audio finishes first, `done` timings present, the error event on VLM failure, provider selection from config.

Live checks: one /ask call per provider with a sample image, plus one benchmark run with at least one model per provider.

Device checks: none.

## P4 — Clip packs

Work:
- `server/phrases.json`: every fixed phrase per language, keyed `{category}.{value}` (§6). It covers the 15 alert classes (`obj.*`), `dir.left|ahead|right`, `dist.near|far`, all system lines in F4, F5, F7, F10 and the tutorial (`sys.*`), and earcons as separate files.
- `scripts/gen_clips.py --langs hi-en,hi,en,ta` → `app/assets/clips/<lang>/<key>.mp3` + `manifest.json`. It is idempotent and skips existing clips unless passed `--force`.
- Commit the generated clips.

Automated tests: every key exists in every language in phrases.json, every manifest entry has a file, and gen_clips works against a fake TTS.

Live checks: generate the hi-en pack. Listen to 10 random clips and note mispronunciations.

Device checks: none (played in P5).

## P5 — App core: metrics, speech scheduler, audio

Work:
- `Metrics`: event IDs, monotonic stage timestamps (§8), a rolling window with p50/p95 per stage, and a JSON export via the share sheet.
- `AudioPlayer` (expo-audio): plays a clip key, a file URI or expo-speech text. It supports preloading the clip pack, stop in ≤ 50 ms, and sequential stitched clips.
- `SpeechScheduler` per F9: priorities P0–P4, P0 interrupts, P1–P2 wait for the current clip, Reflex items older than 500 ms are dropped, alerts from the same frame are coalesced (max 2 objects), and answers are never dropped.
- `ConnectivityMonitor`: netinfo plus a `/health` ping. It exposes `online`.
- Keep-awake while the app is open.
- Debug overlay shell: triple-tap toggles it, and it shows metrics p50/p95.

Automated tests (Jest, fake player and clock): priority order, P0 interrupt, P1 not cutting a clip, the 500 ms stale drop, answers never stale, coalescing, metrics percentiles.

Device checks:
- DT-5.1 Bundled clips play with no audible gap when stitched.
- DT-5.2 A P0 test event interrupts a long answer clip within 100 ms (read the overlay timing).
- DT-5.3 Playback follows the system volume.

## P6 — Reflex lane: detectors, tracker, hazard alerts (F1, F2)

Work:
- `Detector` interface with `YoloDetector` and `EfficientDetDetector`, chosen in config. The frame processor resizes frames, runs the detector on every 2nd–3rd frame and decodes boxes (plus NMS for YOLO).
- Filters: the 15 alert classes, confidence ≥ 0.5, area ≥ 3%.
- Geometry: direction by thirds, and near/far by the F1 rule. Thresholds are config values.
- `Tracker` per F2: greedy class + IoU > 0.3, stable IDs, and re-announce rules covering far → near, a direction change, absent > 3 s, and the per-class 4 s cooldown.
- Utterance builder `[obj] + [dir] + [dist]`, and the F1 priority order, feeding the scheduler.
- Reflex metrics: `frame_ts`, `detect_done`, `enqueued`, `play_start`.
- Overlay: boxes, labels, track IDs, detector ms.
- Quiet-mode flag (wired to a command in P7).
- Model load failure → spoken error and stop (§9).

Automated tests: geometry tables, tracker on scripted box sequences (a chair held still for 30 s → 1 alert, far → near re-announces, the cooldown), priority ordering, the utterance builder, the box decoder for both models on saved raw outputs.

Device checks:
- DT-6.1 Benchmark both detectors (ms per inference, detections/s, GPU vs CPU) and choose the default.
- DT-6.2 A chair about 1.5 m ahead in airplane mode is announced < 100 ms after detection, with the correct direction.
- DT-6.3 Facing one chair for 30 s → exactly one alert.
- DT-6.4 Tune the near/far thresholds while walking toward an object.
- DT-6.5 Phone temperature and battery drain after 15 min of continuous use.

## P7 — Push-to-talk, command router, scene questions (F5, F6)

Work:
- Whole-screen hold-to-talk button: haptic tick on press and release, plus a listening earcon.
- `SttClient`: PCM recorder → `/stt` WebSocket, with a final transcript timeout of 3 s.
- `CommandRouter`: keyword rules for each F5 command in Hindi, Hinglish and English, at least 2 phrasings each. Anything unmatched is a question. Wire up describe, who is here, repeat last, quiet on/off and stop/ruko. Save/delete/list (P9), read (P10) and language (P11) get stub handlers that say "not available yet".
- `AskClient`: builds the AskRequest (512 px JPEG at quality ~70, detections, names, lang) and parses SSE incrementally. Verify that streaming fetch works in React Native (`expo/fetch`, or an SSE library). Each sentence's audio is written to a file and queued at P3.
- A hazard during an answer interrupts it, and there is no resume (F6).
- Offline: questions get "Internet nahi hai".
- Describe metrics: `ptt_release`, `stt_final`, `ask_sent`, `first_sentence_rx`, `play_start`, plus the server's `done` timings. Transcripts are shown on the overlay.

Automated tests: router phrasing tables (every command, ≥ 2 phrasings, unmatched → ask), SSE parser on chunked input split mid-event, AskRequest building, the offline branch, SttClient against a fake WebSocket.

Device checks:
- DT-7.1 Each fixed command works with 2 phrasings.
- DT-7.2 Median release → first audio ≤ 2 s over 20 questions on Wi-Fi and on 4G, run once per VLM provider.
- DT-7.3 A car alert interrupts a long answer within 100 ms.
- DT-7.4 Airplane mode → a question gets "Internet nahi hai", and alerts keep working.

## P8 — Person identification (F3)

Work:
- When a person track exists: ML Kit face detection, a crop with 20% margin, alignment, resize to 112×112, MobileFaceNet, L2-normalise.
- `IdentityStore` on expo-sqlite: name, embeddings and name-clip path. No photos, ever.
- Matcher: cosine similarity, best match per person, threshold 0.65 (config), a 3-of-5 vote, face width ≥ 80 px.
- Unknown after 5 frames ≥ 80 px with no match.
- One announcement per appearance. Re-announce after 5 min absent.
- Utterance `[name clip] + [dir]` at P1. Until P9, a dev-only "seed from a test image" helps with testing.

Automated tests: matching with fixed embedding fixtures (a known person passes, a near-threshold one → unknown, two similar people → bias toward unknown), the voting window, the re-announce timer, SQLite store CRUD with an in-memory adapter.

Device checks:
- DT-8.1 Calibrate the threshold with 3 real people (log the similarity distributions and pick a threshold).
- DT-8.2 Each enrolled person is named within 1 s at 1–2 m.
- DT-8.3 An unenrolled person → "unknown" in 10 of 10 trials, never named.
- DT-8.4 Face pipeline time per frame (target 20–40 ms).

- Remove the P8 dev seed.

Automated tests: name extraction for each phrasing, including multi-word and Hindi-script names; state-machine transitions (consent no → cancel, a timeout, no face, two faces); the deferred-clip retry when back online; delete removing every record and file.

Device checks:

- DT-9.2 Offline enroll → the name is spoken by expo-speech, and the Timbre clip replaces it once back online.
- DT-9.3 Timbre pronunciation of 5 Indian names. Note any that need phonetic spelling (open question §11).

- Check whether ML Kit's Latin model reads Devanagari. Verify which ML Kit script models the plugin exposes, and log it if Hindi needs a separate model.
